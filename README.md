# Очередь перед чекаутом — HTTP-слой и инфраструктура

Сервис ставит покупателей в очередь на дефицитный товар и выдаёт временное право на
покупку, чтобы один экземпляр нельзя было продать дважды.

Здесь моя часть: транспортный слой, защита чекаута от обхода, идемпотентность, миграции
и запуск проекта.

```
backend/
  cmd/api/main.go        сборка приложения: конфиг → пул → миграции → роутер → сервер
  internal/config/       настройки из окружения с проверкой на старте
  internal/db/           пул соединений и раннер миграций
  internal/httpx/        формат ответов, middleware, идемпотентность
  internal/checkout/     оформление покупки по праву
  migrations/            встраивание .sql в бинарь + схема идемпотентности
  Dockerfile             двухстадийная сборка, статический бинарь
deploy/                  nginx-шлюз: статика фронта + прокси на /api
docker-compose.yml       база, бэкенд, шлюз
.golangci.yaml           линтер с обоснованием каждого правила
```

## Чекаут

`POST /api/checkout` — единственное место, где товар превращается в заказ. Знание адреса
не помогает: право проверяется сразу по трём вещам.

```go
orderID, err := h.grants.ConsumeGrant(ctx, userID, req.ProductID, req.GrantToken)
```

Все отказы дают 403 и различаются только кодом в теле: `no_active_grant`, `grant_expired`,
`grant_consumed`, `grant_forbidden`. Статус у всех одинаковый намеренно. Отдавай мы разные
коды, чекаут превратился бы в оракул, по которому можно перебирать чужие токены и понимать,
какие из них вообще существуют.

Интерфейс `GrantConsumer` объявлен на стороне чекаута, а не в пакете очереди. Поэтому
чекаут не зависит от устройства ядра и тестируется без базы.

## Middleware

```
RequestID → Recoverer → Logger → CORS      общие, на всех
RequireUser → RateLimit → Idempotency      только на том, что меняет состояние
```

Граница защиты собрана списком в одном месте, так что добавить маршрут мимо неё случайно
не выйдет:

```go
root.Handle("/api/products/{id}/queue", guarded)
root.Handle("/api/products/{id}/queue/status", guarded)
root.Handle("/api/products/{id}/waitlist", guarded)
root.Handle("POST /api/checkout", guarded)
```

Порядок внутри цепочки не произвольный. Лимит запросов считается по `X-User-Id`, значит
его нельзя поставить раньше проверки этого заголовка. Авторизации в сервисе нет по условию
задачи, пользователь так и приходит — заголовком, но значение всё равно недоверенное, и
`RequireUser` проверяет набор символов и длину, а не просто непустоту.

## Идемпотентность

Клиент генерирует `Idempotency-Key` один раз на намерение. Без этого двойной клик по
«Купить» занял бы два места в очереди.

Занятие ключа — одна атомарная вставка. Кто вставил строку, тот и выполняет запрос,
проигравший читает сохранённый ответ. Если бы мы сначала проверяли наличие ключа, а потом
вставляли, сама защита от гонки стала бы гонкой.

```sql
INSERT INTO idempotency_keys (user_id, idempotency_key, request_hash)
VALUES ($1, $2, $3)
ON CONFLICT (user_id, idempotency_key) DO NOTHING
```

В схеме три вещи, каждая закрывает свою дыру. Ключ уникален в паре с пользователем, а не
сам по себе, иначе чужой `Idempotency-Key` дал бы прочитать чужой ответ. `request_hash`
ловит переиспользование ключа для другого намерения: такой запрос получает 409, а не старый
ответ. Тело хранится как `bytea`, потому что `jsonb` пересобрал бы JSON и повтор перестал
бы быть тем же ответом байт в байт.

Ответы 5xx не запоминаются, а запись удаляется. Сбой временный, и повтор должен
действительно повториться, а не вечно отдавать ту же ошибку.

## Миграции

Свой раннер вместо готовой библиотеки, 113 строк без внешних зависимостей. Файлы
применяются по порядку номеров, каждый в своей транзакции вместе с отметкой в
`schema_migrations`: либо применился и учтён, либо ни то, ни другое.

Ради одной детали всё это и писалось: пустые файлы пропускаются и не отмечаются
применёнными. Пока схема дописывалась, незаполненные заглушки не мешали поднимать стек,
а как только в файле появлялся SQL, он применялся сам.

Перед накатом берётся advisory-lock, чтобы две одновременно стартующие копии сервиса не
применили одно и то же дважды. Сами миграции вшиты в бинарь через `go:embed` — на сервер
уезжает один самодостаточный файл, запустить его без схемы не получится.

## Почему так, а не иначе

### Роутинг на стандартной библиотеке

С Go 1.22 встроенный `http.ServeMux` умеет и методы, и параметры пути, а middleware —
обычные `func(http.Handler) http.Handler`. Сторонний роутер не понадобился.

### Ответы только через httpx.JSON и httpx.Error

Коды ошибок лежат константами в одном файле. Фронт ветвит сценарий по этим строкам, так
что опечатка в любой из них сломала бы экран.

### Проверка конфигурации на старте

Опечатка в `GRANT_TTL_SECONDS` при ленивом разборе вылезла бы у первого вставшего в
очередь и выглядела бы как баг очереди. Сервис вместо этого просто не поднимется и скажет,
что именно не так.

### Отдельный контекст для остановки

Сигнальный контекст к моменту `Shutdown` уже отменён, и на нём сервер оборвал бы активные
запросы мгновенно. Отдельный даёт десять секунд доиграть тем, кто прямо сейчас оформляет
покупку.

### Один origin для фронта и API

nginx отдаёт статику и проксирует `/api`. В проде из-за этого нет CORS, а снаружи всё
выглядит как одна ссылка без портов. Буферизация на `/api` выключена: статус опрашивается
раз в две секунды, и лишняя задержка бьёт по отсчёту TTL.

## Тесты

Проверяется то, что легко сломать незаметно:

- четыре причины отказа в праве — нет права, истекло, использовано, чужое;
- `product_id` доезжает до ядра, иначе токен от одного товара сработал бы для другого;
- без `X-User-Id` ядро не вызывается вообще;
- подробности внутренней ошибки не утекают клиенту;
- `X-User-Id` с переводом строки внутри отвергается, это попытка подделать логи;
- лимит запросов исчерпывается и не протекает между пользователями;
- паника превращается в 500 с телом по контракту, а не рвёт соединение.

Вместо ядра подставляется заглушка, поэтому тесты идут без базы и укладываются в секунды.
